## 1. Процесс разработки (по шагам задания)

### Шаг 1 — подготовка ТЗ
Использовано готовое ТЗ из ДЗ3 (`../ДЗ3/technical_specification.md`, 70 FR + 18 NFR): стек React + Vite + Tailwind CSS зафиксирован ещё в требованиях ДЗ1–2; реализованы все 4 функции MVP (управление привычками, ежедневная отметка, серии и статистика, аккаунт — Mock-режим с баннером до ДЗ5).

### Шаг 2 — инициализация проекта (агентом)
Каркас создан агентом в основной сессии: `package.json`, `vite.config.js` (React + Tailwind v4 + Vitest), `index.html`, `App.jsx` с нижней навигацией, каркасы трёх экранов. Дизайн-токены перенесены из HTML-макета Концепции 1 (`ДЗ3/ui_concepts/концепция-1-минимализм.html`) в `src/index.css` один в один — палитра «тёплая бумага + шалфей». **Файл `.cursorrules`-эквивалент из ДЗ2 применён:** `CLAUDE.md` скопирован в корень приложения и далее соблюдался каждым агентом. Проверка: `npm install` + `npm run build` зелёные. Коммит `f66e346`.

### Шаги 3–4 — генерация компонентов (6 агентов параллельно)
Ключевая техника — **«контракты до кода»** (та же методика Chain-of-Thought из ДЗ2): до генерации я зафиксировал интерфейсы — модель данных (`Habit`, `CheckIn`), API Mock-слоя (8 функций), сигнатуры утилит, пропсы каждого компонента — и раздал их шести параллельным агентам:

| Агент | Что создал | Самопроверка |
|---|---|---|
| `gen:utils` | Порт утилит ДЗ2 в ESM: `stats.js` (4 функции), `format.js` (+ публичная `formatDayMonth`) | 84 теста Vitest |
| `gen:data` | `src/data/api.js`: Mock-API (localStorage, seed 6 привычек с разными паттернами серий, задержка 150–400 мс, режим ошибки `setMockError`) | 41 автопроверка |
| `gen:ui-core` | 7 компонентов по макету Концепции 1: HabitCard (чекбокс 44px), WeekDots, StreakBadge, DaySummary, EmptyState, HabitDialog (FR-6..9), ErrorBanner | 92 теста + сборка |
| `gen:today` | экран «Сегодня» + хук `useHabitsData` (оптимистичные отметки с откатом, тихий reload) | 4 теста хука |
| `gen:stats` | экран «Статистика» + WeekBars + StatsCalendar (чипы, серии, календарь, % месяца) | 16 тестов |
| `gen:profile` | экран «Профиль» (редактирование, архив с подтверждением, восстановление, баннер локального режима) | 7 тестов |

Каждый агент обязан был прочитать `CLAUDE.md` и следовать правилам — и следовал: JSDoc на всех функциях, состояния loading/error/success (правило 5), ARIA-атрибуты, никаких новых зависимостей (правило 8 соблюдено — в `package.json` только react/react-dom).

**Интеграция после параллельной генерации: `npm run build` и полный прогон тестов прошли с первого раза** — 108 тестов, 7 файлов, 0 правок на стыках. Контрактный подход окупился: агенты стыковались по зафиксированным интерфейсам, а не по догадкам.

### Шаг 5 — тестирование и отладка
- **Автотесты: 108 шт.** (порог задания — 3): 84 теста логики портированы из ДЗ2 (все краевые случаи дат — переходы месяца/года, високосный, DST), 24 новых — компонентные и экранные (Testing Library), включая поведение при сетевом сбое (`setMockError(true)` → откат оптимистичной отметки, баннер с «Повторить»).
- **Отладка рендера «мультимодально»:** приложение поднято на dev-сервере и снято headless-браузером на трёх разрешениях (390/768/1280, все три экрана через глубокие ссылки `#today/#stats/#profile`). Проверка скриншотов: (а) `--dump-dom` — в отрисованном DOM присутствуют все 6 привычек, серии «🔥 12/5/3/2», блоки статистики и архива; (б) пиксельный анализ — 65–133 различных цветов на сетке выборки (пустая страница дала бы 1–3); (в) финальный визуальный контроль — пользователем (скриншоты в `скриншоты/`).
- **Консоль:** `console.error` встречается только в ожидаемом месте — тест демо-сбоя сети.

### Шаг 6 — адаптивная верстка
Мобильный макет 390px — основной (`max-w-md` колонка по центру, нижняя навигация `fixed`); FAB «+» позиционирован `right-[max(1rem,calc(50%_-_13rem))]` — прижимается к колонке контента на широких экранах. Сняты и приложены скриншоты 390/768/1280 — интерфейс читается на всех трёх, вёрстка не ломается.

### Шаг 7 — оптимизация и рефакторинг
- Хук данных: защита от устаревших ответов (`requestIdRef`), «тихий» reload после мутаций (без мигания скелетонов), хирургический откат одной отметки при сбое.
- Логика — только чистые функции в `utils/` (легко тестируются, переиспользуются из ДЗ2 без изменений).
- Добавлены глубокие ссылки на вкладки (`location.hash`) — прямой доступ к экранам для тестов и скриншотов.

## 2. Применённые техники работы с AI (с примерами промптов)

1. **Контракты до кода.** Промпт каждому агенту начинался с точных интерфейсов:
   > «Контракт stats.js: `getCurrentStreak(checkIns, habitId, today?)`, `getBestStreak(checkIns, habitId) -> {length,start,end}|null`, `getCompletionRate(checkIns, habit, period, today?) -> {percent,done,expected}`, `groupByWeeks(checkIns, habitId, options?)`.»
   
   Результат: 6 агентов работали параллельно над одним приложением без единого конфликтного слияния.
2. **Правила проекта как системный промпт.** Каждый промпт: «ОБЯЗАТЕЛЬНО: перед работой прочитай правила проекта CLAUDE.md и следуй каждому правилу». Агенты цитировали правила в решениях (например, DaySummary не рендерится при total=0 со ссылкой «FR-21 — никаких нулевых счётчиков»).
3. **ТЗ как источник требований.** Компоненты строились по номерам требований: диалог — «по FR-6..FR-9», архивация — «FR-17..FR-19», баннер локального режима — «FR-58 в адаптации Mock-режима ДЗ4».
4. **Визуальный образец в промпте.** UI-агенту указан путь к HTML-макету Концепции 1 — компоненты наследуют макет, а не выдумывают стиль.
5. **Самопроверка в промпте.** Каждый агент обязан прогнать свои тесты/сборку и отчитаться фактическими цифрами («84 теста, все прошли»), а не уверениями.

## 3. Проблемы и решения

| Проблема | Решение |
|---|---|
| Гонка дизайн-токенов: ui-core добавил `--color-terracotta` в `index.css`, profile-агент на старте его не видел (помечал как «стили тихо деградируют») | Токен добавлен одним агентом и подхвачен остальными через общий файл; финальная проверка grep + сборка подтвердили наличие. Урок: дизайн-токены должны быть частью каркаса до параллельной генерации |
| Экраны генерировались раньше готовых компонентов (параллельность) | Импорты по контрактным путям; интеграционная сборка прошла с первого раза |
| Промежуточный прогон profile-агента видел 1 падающий тест соседнего хука (файл ещё дописывался) | Итоговый полный прогон: 108/108 — файлы финализировались до интеграции |
| Визуальный канал проверки скриншотов недоступен агенту в этой сессии | Тройная объективная проверка: dump-dom (контент), пиксельный анализ (не пусто), финальный просмотр пользователем |

## 4. Выводы и рекомендации

1. **Параллельная генерация по контрактам** ускорила разработку ~в 6 раз (6 агентов одновременно) при нулевой цене интеграции — но только потому, что интерфейсы были зафиксированы заранее; «контракты → код» теперь наш стандарт для ДЗ5 (там же ляжет на SQL-схему и API).
2. **Переиспользование ДЗ2 окупилось дважды:** утилиты переехали без изменения логики (63 теста дат поехали вместе с ними бесплатно), а правила CLAUDE.md дисциплинировали всех агентов (JSDoc, состояния, ARIA — без напоминаний).
3. **Mock-слой с режимом ошибки** (`setMockError`) сделал error-состояния тестируемыми и воспроизводимыми — обязательная практика до появления реального бэкенда; в ДЗ5 тот же приём повторим уже против Supabase.
4. **Скриншотная отладка headless-браузером** дешевле ручной: глубокие ссылки позволили снимать любой экран без кликов — приём переносится в CI (ДЗ6).
