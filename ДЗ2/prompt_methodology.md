# ДЗ2 · Шаг 4 — Применение Chain-of-Thought (prompt_methodology.md)

## Задача

**«Модуль статистики трекера привычек»** — сложная задача разработки: четыре функции (текущая серия, лучшая серия за всё время, процент выполнения за период, группировка отметок по неделям), насыщенная календарными краевыми случаями (границы месяцев/лет, високосный год, таймзоны/DST, «живая» серия, знаменатель процента). Задача выбрана потому, что одним промптом «напиши модуль статистики» легко получить поверхностное решение без продуманных краевых случаев.

## Метод

Chain-of-Thought: задача разбита на **3 логических шага**, каждый шаг — отдельный промпт отдельному «свежему» AI-агенту (Claude Code), результат предыдущего шага передаётся в следующий промпт. Агенты работали с реальной файловой системой: писали файлы и прогоняли тесты.

| Шаг | Промпт (кратко) | Результат | Артефакт |
|---|---|---|---|
| 1 | Спроектируй КОНТРАКТ модуля — только интерфейс, без реализации | Контракт: структуры данных, 4 функции с JSDoc-сигнатурами, **21 краевой случай** | раздел ниже (полный текст ответа — `статистика/` в описании к сдаче) |
| 2 | Реализуй модль **строго по контракту** шага 1 | `stats.js`, 405 строк, чистые функции, UTC-арифметика; агент сам прогнал 36 smoke-проверок контракта и 19 существующих тестов проекта | `статистика/stats.js` |
| 3 | Напиши юнит-тесты (node:test) по контракту и коду | 63 детерминированных теста (596 строк), все зелёные | `статистика/stats.test.js` |

Итоговый прогон всего ДЗ2: `node --test` → **94/94** (63 статистика + 18 format «с правилами» + 13 format «без правил»).

## Промпты цепочки (полные тексты)

### Шаг 1 — контракт

> Ты — AI-агент (Claude Code), работаешь в проекте «Трекер привычек»: веб-приложение, привычки с ежедневными отметками (формат YYYY-MM-DD), серии, статистика. Стек: JavaScript (ES-модули, совместимые с Node и браузером), тесты node:test. Твой финальный текст — данные для документа, верни только результат без вступлений.
>
> ЗАДАЧА (шаг 1 из 3, цепочка Chain-of-Thought): спроектируй КОНТРАКТ модуля статистики src/utils/stats.js — только интерфейс, БЕЗ реализации.
> Верни Markdown: 1) входные структуры данных (что принимает модуль: записи отметок, список привычек — с примерами); 2) экспортируемые функции с сигнатурами в виде JSDoc-заглушек: текущая серия, лучшая серия за всё время, процент выполнения за период, группировка отметок по неделям; 3) перечень краевых случаев, которые обязан учесть каждый потребитель контракта.
> Помни: это промежуточный шаг цепочки — реализации не будет, только контракт.

### Шаг 2 — реализация (на вход подан результат шага 1)

> ЗАДАЧА (шаг 2 из 3, цепочка Chain-of-Thought): реализуй модуль статистики СТРОГО по контракту ниже (результат шага 1).
> Требования: чистые функции, без внешних зависимостей, JSDoc на каждой экспортной функции, 'use strict', экспорт через module.exports для Node и одновременно window для браузера. Все краевые случаи из контракта обработай.
> Верни полный код одним блоком js с указанием пути файла.
>
> КОНТРАКТ (шаг 1): <полный текст контракта из шага 1>

### Шаг 3 — тесты (на вход подан код шага 2)

> ЗАДАЧА (шаг 3 из 3, цепочка Chain-of-Thought): напиши юнит-тесты (node:test) для модуля статистики ниже (результат шага 2).
> Покрой: позитивные сценарии по каждой функции и ВСЕ краевые случаи из контракта (пустые данные, границы периодов, переходы месяца/года, вчерашняя/сегодняшняя последняя отметка). Времена детерминированные — «сегодня» передаётся параметром.
> Верни полный файл тестов одним блоком js с указанием пути.

## Что дал каждый шаг (наблюдения)

1. **Контракт до кода.** Шаг 1 выдал 21 краевой случай ДО написания реализации — включая ровно тот класс бага, который реально случился в ДЗ1 (сравнение `getDate()` вместо полной даты на границе месяца) и тонкости таймзон (дни по 23/25 часов при DST → `Math.round`). При прямой генерации «одним промптом» большинство этих случаев не всплыло бы.
2. **Дисциплина реализации.** Шаг 2 получил контракт как ограничение: чистые функции, инъекция «сегодня», идемпотентность входов (дубли/неотсортированность), `TypeError` на невалидные даты вместо тихого `NaN`. Агент самостоятельно прогнал 36 smoke-проверок контракта и убедился, что не сломал 19 существующих тестов проекта.
3. **Тесты как замыкание цепочки.** Шаг 3 писал тесты против зафиксированного контракта и готового кода — получилось 63 теста, включая переход года, високосный февраль 2024, недели через границу месяца/года, немутабельность входных массивов.
4. **Вывод по методике.** Разбиение на «контракт → реализация → тесты» превратило одну расплывчатую задачу в три проверяемых; каждый следующий промпт опирается на артефакт, а не на память чата. Это же свойство CoT пригодится в ДЗ4 при разработке компонентов по ТЗ.
